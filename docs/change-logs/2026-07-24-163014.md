# Stats, Scheduler, Achievement, and Load-Test Hardening

## What Changed

### Stats

- Replaced the mixed Stats payload with a bounded timeline contract containing day/month granularity, terminal outcome counts, pending snapshots, and net EXP.
- Made `timezone_offset` optional while preserving explicit `0` as UTC.
- Defined 7/30/90-day periods as exact local calendar days; all-time uses monthly buckets and the heatmap remains capped at 365 days.
- Used authoritative outcome timestamps and actual earned EXP or penalties.
- Consolidated repeated scans into filtered aggregate queries and partial outcome indexes.

### Frontend

- Added TanStack React Query with keys `["stats", period, timezoneOffset]`, 30-second stale time, five-minute garbage collection, request deduplication, retained prior data, and transient-only retry.
- Prefetched common periods and invalidated Stats after task and goal mutations.
- Displayed failed separately from overdue, used day/month labels and net EXP, memoized chart data, and disabled repeated chart animation.

### Scheduler

- Runs exact overdue detection every minute in committed 500-row batches using `(due_date, id)`, `FOR UPDATE SKIP LOCKED`, and the existing advisory lock.
- Applies grouped user penalties through bounded set-based updates.
- Creates only the first valid recurring occurrence strictly after the current time.
- Selects perfect-day candidates in one timezone-aware grouped query.
- Uses a small independent pool, coalescing, misfire grace periods, non-fatal startup catch-up, and persisted heartbeat/error state.
- Added read-only `GET /api/health/scheduler`.

### Achievements

- Uses `INSERT ... ON CONFLICT` for stat creation and locks the per-user stat row before counter/streak updates.
- Derives local completion date/hour from server timestamps and stored timezone; legacy client parameters are accepted but ignored.
- Checks only affected badge categories.
- Refreshes locked user rows from PostgreSQL, fixing lost EXP updates caused by stale SQLAlchemy identity-map values during concurrent completions.

### Migration and Load Harness

- Migration `20260724_02` adds/backfills `tasks.cancelled_at`, replaces timestamp indexes, adds the overdue claim index, and creates `scheduler_state`.
- The migration introspects existing objects so long-lived and fresh databases both work despite the legacy baseline using current metadata.
- Added the isolated `leveling-system-load` Compose project, deterministic smoke/capacity/heavy seed profiles, k6 Stats/mixed/write/spike scenarios, and scheduler/concurrency benchmarks.
- Generated tokens, k6 summaries, and Docker snapshots live under ignored `load-tests/results`.

## Why

The previous Stats path repeatedly scanned task history, mixed pending state with period outcomes, and used inconsistent timestamps. The scheduler did unbounded/per-user work, while concurrent task completions could lose EXP increments. These changes bound memory and payloads, reduce database round trips, preserve immediate transactional badge feedback, and establish evidence before adding distributed infrastructure.

## Known Limits

- The personal Docker stack intentionally runs one API worker; the tested 100 RPS topology uses four.
- Local k6 results are a regression gate, not cloud-capacity proof.
- Mixed, write, and spike profiles are implemented but were not run in this change.
- Redis, PgBouncer, replicas, rollup tables, queues, and outbox delivery remain deferred.
- The legacy baseline migration's dynamic `create_all` should eventually become a frozen schema migration.
