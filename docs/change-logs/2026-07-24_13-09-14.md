# Bounded Task Loading and Virtualized Calendars

## What Changed

- Added cursor-paginated task endpoints:
  - `GET /api/tasks/page`
  - `GET /api/tasks/range/page`
- Added paginated goal summaries and grouped milestones:
  - `GET /api/goals/page`
  - `GET /api/goals/{goal_id}/milestones/page`
- Kept legacy list routes for compatibility, marked them deprecated, and added a 1,000-record overflow guard.
- Added stable `(date, id)` cursor ordering and user-scoped filtering.
- Added Alembic revision `20260724_01` with cursor-friendly task and goal indexes.
- Corrected timezone-aware task range boundaries to convert to UTC before removing timezone information.
- Reworked Calendar to keep only the previous, visible, and next months resident.
- Added stale-request cancellation, bounded cache eviction, retry state, and automatic accumulation of 200-item API pages.
- Grouped tasks once by local date instead of filtering the complete loaded list for every day.
- Added TanStack Virtual for horizontal day columns and day lists above 50 visible tasks.
- Migrated Goals to 25-item summary pages and intersection-triggered 50-item milestone pages.
- Added Vitest and focused backend pagination tests.

## Why

The old Calendar fetched one month per request but retained as many as 12 months and rendered every day column. General task and goal routes could also return unbounded task collections. Long-running or high-volume accounts would therefore increase database work, response size, browser memory, repeated filtering, and DOM size.

The new contracts bound each response, retain stable navigation across tied timestamps, and keep the browser's resident calendar window fixed while preserving all tasks for those months.

## API Contracts

- Task pages default to 100 items and allow at most 200.
- Calendar range pages reject windows longer than 32 days.
- Goal pages default to 25 items and allow at most 100.
- Milestone pages default to 50 grouped titles and allow at most 100.
- Page responses use `{ items, next_cursor, has_more }`.
- Malformed cursors return `400`; ownership filters are applied before cursor conditions.
- Legacy list calls above 1,000 records return `413` and direct clients to the paginated replacement.
